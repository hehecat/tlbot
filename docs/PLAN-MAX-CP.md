# Max ΔCP/h 的形式化与实现

更新时间：2026-11-16 · 对应 `src/planner.mjs` · 端点 `GET /plan`

## 1. 问题

给定状态 S（等级、经验、金币、元宝、装备、珍兽、背包、封印、栏位）与时间窗 T（默认 1 小时），
在资源约束下选择动作集合 A，使期望战力增量最大化：

```
maximize   Σ_a  ΔCP(a) · n_a
subject to Σ_a  exp(a)·n_a   ≤ E(T)          （角色经验，≈60M/h）
           Σ_a  gold(a)·n_a  ≤ G(T)          （金币，≈250k/h）
           Σ_a  yuanbao(a)·n_a ≤ 0           （用户硬约束：零元宝）
           Σ_a  time(a)·n_a  ≤ 60 min
           slots(a)          ≤ 空栏位
           seals(a)          ≤ 无相印
           n_a ∈ {0..cap_a}，一次性动作 cap_a=1
```

## 2. 为什么可以分解

四类资源几乎不重叠，因此用**多资源背包的贪心近似**：

1. 对每个动作算它占用最紧的那项预算的比例
   `share(a) = max(exp/E, gold/G, time/60, slots/free)`
   （元宝 >0 直接禁用）。
2. 优先级 `priority(a) = ΔCP(a) / share(a)`，按优先级降序执行。
3. 每个资源维度上，这就是「单位资源换战力」排序：经验看 CP/M exp，金币看 CP/金，时间看 CP/h。
4. `share>1` 表示一小时内做不完，动作进入「跨小时累积」队列（例如 3M 金币的塔、160.8M 经验的一级）。

`/plan` 的输出同时给出：
- `expAllocation`：当前经验的最优去向（按 CP/M exp 排序后的第一项）
- `expActions[]`：所有经验去向的 CP/M exp 与每小时战力
- `oneOffActions[]`：一次性动作的 ΔCP、成本、`priority`、`binding`（最紧资源）
- `plan[]`：Top 5 可执行动作
- `summary.stableCpPerHour`：稳定速率（经验转化 + 到点繁殖），不含一次性库存
- `dataGaps[]`：未标定的系数

## 5. 与 System2 的接口

System2 每 30 分钟（DSH schedule）：
1. `GET /plan?live=1` 读预算/优先级；
2. 只执行 `plan[0]` 中 `available=true` 且不需要花元宝的动作；
3. 执行后对比 power/资源，写 `data/decisions.jsonl`；
4. 没有可执行动作就回一行「无动作：原因」。

System1（引擎）负责：战斗、心跳、后勤、日常、繁殖到点自动 claim、自愈、看门狗。
两者之间只通过 HTTP 状态与 `data/*.jsonl` 通信，不共享进程内内存。
